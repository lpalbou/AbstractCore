Reasoning Control

AbstractCore exposes one parameter — thinking= — for every provider that can reason, and maps it to whatever control surface each backend actually honors. This page explains what you can request, what each provider does with the request, and how to verify from the response that your request took effect.

Request a reasoning mode

from abstractcore import create_llm

llm = create_llm("mlx", model="mlx-community/Qwen3.8-27B-4bit")

llm.generate("Plan the migration", thinking=None)      # model/server default
llm.generate("Plan the migration", thinking="off")     # no reasoning ("none" is an alias)
llm.generate("Plan the migration", thinking="on")      # reasoning enabled, model default depth
llm.generate("Plan the migration", thinking="low")     # brief reasoning
llm.generate("Plan the migration", thinking="medium")  # balanced
llm.generate("Plan the migration", thinking="xhigh")   # deepest, when the model offers it

Accepted values: None / "auto", True / "on", False / "off" / "none", and the levels "minimal", "low", "medium", "high", "xhigh" ("extra high" is an alias for "xhigh").

When a model advertises a specific effort enum, a level outside that enum is mapped to the nearest supported one and the substitution is reported as a RuntimeWarning. Requesting "high" from a model offering low | medium | xhigh therefore runs at medium.

Reasoning text, when the model emits it, is available as response.reasoning, and response.content stays clean.

Precedence

Several things can set the reasoning of one call. The first that applies wins:

  1. thinking= on the call. thinking="auto" (or None passed through an API that distinguishes it) means "no control": nothing is sent and no configured default is added.
  2. A provider-native reasoning field on the call: reasoning_effort=, reasoning= (LM Studio's native endpoint, OpenRouter's object), or think= (Ollama). It is sent as given, without level mapping.
  3. The reasoning effort configured on the text route (abstractcore config set-default input.text --reasoning <level>, or the gateway console). It applies only when the route describes the instance serving the call: the same provider, or the same endpoint profile (endpoint:<id>), and the same model. A route that sets only a reasoning effort, with no provider or model, applies to every instance. An effort configured for another backend is not a fact about this one, so it is not applied.
  4. Nothing. The model or server default stays in effect.

Before 2026-10-25, step 3 applied to every call that did not pass thinking=. A machine configured with reasoning: minimal for one route therefore sent reasoning_effort: "low" for generate(..., reasoning_effort="high") and on unrelated models.

response.metadata["thinking_source"] records which step applied: "thinking", "reasoning_effort" (a raw field), or "configured_default". For a raw reasoning_effort=, thinking_requested is the value you passed ("none" reads as "off"). thinking_effective repeats it only on providers that forward the field verbatim (OpenAI and the OpenAI-compatible family, LM Studio and vLLM included). OpenRouter is excluded, because it documents a reasoning object rather than a top-level reasoning_effort. The route summary in response.metadata["_resolved_generate_route"] reports a configured effort that was not applied as reasoning: None, with reasoning_source set to not_applied:<reason>.

When a call passes both thinking= and reasoning_effort=, providers differ. OpenAI and generic OpenAI-compatible servers send the thinking= mapping in place of your field. LM Studio sends your field. vLLM and OpenRouter send your top-level field next to their own mapping (chat_template_kwargs, or the reasoning object), so the server decides between them. Pass one or the other.

LM Studio facts

LM Studio's OpenAI-compatible endpoint behaves differently from vLLM, so its lane is pinned by live evidence (2026-10-25, qwen/qwen3.6-35b-a3b MLX and qwen/qwen3.8-27b, rendered prompts read back with lms log stream -s model --filter input):

  • chat_template_kwargs, at the top level or under extra_body, and top-level template variables such as enable_thinking are ignored. AbstractCore still sends them, but never counts them as an applied control.
  • The top-level reasoning_effort field reaches the chat template on every request shape: plain prompts, message histories, and tool calls with tool-result history, on both the sync and async paths. "none" renders the template's own empty think block. For an on/off model such as Qwen3.6, every other value turns thinking on and produces the same reasoning. For Qwen3.8, LM Studio applies the level, mapping minimal to low and high to xhigh on its side.
  • LM Studio's per-model default can be thinking off. thinking=True turns it on through reasoning_effort, and the metadata reports what was sent.
  • The assistant no-think prefill is not needed once reasoning_effort: "none" is sent. Sending both renders the empty think block twice. AbstractCore uses the prefill only as the off switch of last resort, when the server has rejected reasoning_effort earlier in the session.
  • The native REST endpoint (POST /api/v1/chat, field reasoning) cannot carry message history, custom tools, or structured output, so thinking= does not route there. Pass reasoning= explicitly to use that endpoint for a plain prompt.

Local providers serialize prompts themselves, so their controls are prompt artifacts rather than API fields. AbstractCore reproduces the artifact the model's own chat template would produce, which keeps a controlled request inside the model's training distribution.

Model requirements

A level request is enforced only when the model's registry entry declares a control surface for it — thinking_control.effort_template_kwarg for backends that render the template, and thinking_control.effort_system_lines for lanes that serialize prompts locally, with reasoning_levels listing the accepted enum. Qwen3.8 declares all three and supports low, medium, and xhigh.

Models whose templates expose only an on/off switch — Qwen3.6, for example — accept thinking="off" and thinking="on", and treat a level request as "reasoning enabled" with a RuntimeWarning explaining that effort scaling is unavailable. To add support for a new model, declare its surfaces in abstractcore/assets/architecture_formats.json or model_capabilities.json; no provider code changes are required.

Verify what actually happened

Every response carries the request and its outcome in response.metadata:

response = llm.generate("Plan the migration", thinking="low")
print(response.metadata["thinking_requested"])      # "low"
print(response.metadata["thinking_effective"])      # "low" when enforced
print(response.metadata["thinking_handled_level"])  # True when a real artifact was applied
  • thinking_requested / thinking_effective — what you asked for, and what the request became after mapping.
  • thinking_handled_enable_disable / thinking_handled_level — whether the on/off switch and the effort level were actually applied.
  • thinking_supported_levels — the model's advertised effort enum.
  • thinking_supports_output / thinking_supports_control — whether the model emits reasoning, and whether it exposes a request-side knob.

thinking_effective reports a level only when a control artifact reached the model. When a request cannot be honored, the field reflects the weaker control that was applied and a RuntimeWarning states what remains in effect, so a silently ignored request never reads as a successful one.

Requests that fall back

A few request shapes are served by a code path that carries no control artifact. AbstractCore declines the claim for these rather than reporting an unenforced level:

  • Prefilled system blocs. In KV cache modes where the system block is already committed to the cache, the effort instruction cannot be inserted. Disabling reasoning still works, because that control lives at the generation boundary.
  • HuggingFace GGUF with structured output, media, tool-role or content-part histories, and when ABSTRACTCORE_GGUF_CONTROL_PLANE=0 disables the local renderer. These requests are served by llama-cpp-python's chat-completion path, which renders no control artifact.
  • Servers that reject reasoning_effort. AbstractCore drops the field, retries the request once so it still succeeds, and warns that the level was not applied. On LM Studio the rejection is remembered for the session: later requests decline the claim, and thinking="off" falls back to the assistant no-think prefill when the model declares one.

Reasoning control and prompt caching

An effort instruction is part of the system block, so changing levels changes the first tokens of the prompt. A durable prompt-cache bloc built at one effort level will not prefix-match a request at another, and the prompt is recomputed. Pin one level per cached session to keep prefixes warm. See Prompt Caching.
