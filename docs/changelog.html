[2.35.0] - 2026-11-10

Added

  • Context7 re-indexes the user docs after each release (.github/workflows/release.yml, context7.json). Once the release is on PyPI the workflow asks Context7 to re-index this repository, so coding agents reading AbstractCore through the Context7 MCP see the published version. context7.json limits the index to the user docs (docs/, the README and the llms files), keeping the backlog, ADRs, reports and sources out. The only credential is CONTEXT7_API_KEY in the GitHub environment context7; without it the job reports a warning and does nothing, and required reviewers on that environment turn the refresh into an approved step. The same step runs on demand from the Actions tab (context7-refresh.yml) after a docs-only change.
  • Current vendor lineups are in the capability registry (assets/model_capabilities.json, assets/architecture_formats.json), so an input.image, input.video or input.voice route can name them instead of the text-only architecture default. POST /v1/audio/transcriptions on a local engine answers {text, language, detected_language}.
  • AbstractCore installs in one line, with no admin rights and no Python needed (scripts/install.sh, scripts/install.ps1). curl -LsSf https://abstractframework.ai/core/install.sh | sh on macOS and Linux, powershell -ExecutionPolicy ByPass -c "irm https://abstractframework.ai/core/install.ps1 | iex" on Windows: the script gets uv when it is missing and Python 3.12 through uv, picks the install setting from the machine (Apple Silicon with macOS 14 or later: abstractcore[apple]; an NVIDIA card or ROCm: abstractcore[gpu]; anything else: the light install), and installs AbstractCore alone as a uv tool, pinned to this release, with the abstractcore, abstractcore-config, abstractcore-chat and abstractcore-endpoint commands and the apps on PATH. It never starts a compiler: llama.cpp comes from upstream's prebuilt Metal or CPU build, and the two optional packages without wheels (echo cancellation, stable-diffusion.cpp) are left out. With an NVIDIA card the gpu setting then gets llama.cpp's CUDA build matching PyTorch's CUDA (cu130 or cu125; on Windows cu130, cu132 or cu125), kept only when it loads the way AbstractCore loads it and llama_supports_gpu_offload() is True, else the CPU build with the reason (ROCm included). On Windows the gpu setting also gets PyTorch's CUDA build for the driver. Every step prints its command; --print shows the plan and changes nothing; running it again upgrades in place and keeps the setting; --profile, --pin VERSION|latest and --from PATH choose otherwise. On a machine where AbstractFramework's installer already provides the abstractcore command, it stops and says so (a standalone AbstractCore beside the framework's gateway tool is not supported). A curl | sh cut mid-download runs nothing (the script runs from one function called on its last line); an nvidia-smi that does not answer is named as the reason; the summary names what the prebuilt-only rule leaves out (echo cancellation, stable-diffusion.cpp); Windows takes -DryRun and -Verbose. See One-line install.

Changed

  • Console theme copy regenerated from ui-kit 0.9.27 (abstractcore/console/themes.py, abstractcore/console/theme_sync.py). The colours and fonts are unchanged; the recorded kit version and the floor the theme test checks against (KIT_THEME_FLOOR) move to 0.9.27, the kit the apps are built on.

Fixed

  • A settings file that cannot be parsed stops the program instead of being renamed and replaced by defaults (abstractcore/config/manager.py, abstractcore/config/provider_profiles.py, abstractcore/server/app.py). The loader raises ConfigParseError with the file path and the parse error (OSError when the file cannot be read); the file is never copied to abstractcore.json.corrupt-<ts>.bak, never shadowed by default settings, and no later save can overwrite it. A provider profile's family is accepted as written while the provider registry is still importing (it is validated when the profile is used), so a load that happens during import abstractcore no longer fails. The abstractcore config CLI prints the error and exits with status 1, and the server refuses to start on such a file instead of coming up with no settings. ConfigParseError is exported from abstractcore.config.
  • GGUF and MLX re-packagings of a registered model resolve to its entry (architectures/detection.py). An Ollama or LM Studio quant tag after the repo name (unsloth/Qwen3.8-27B-GGUF:Q4_K_M, hf.co/...:UD-Q4_K_XL, ...:latest), the OptiQ-4bit, oQ4e and i1 quantizer markers, bartowski's and mradermacher's Org_Model-GGUF repo names, and a re-packaged tail whose base alias is declared only as org/Model (the dated Mistral and Devstral names) all resolved to nothing and fell back to the text-only architecture default. They now reach the registry entry of the model they wrap; a dedicated FP8 or GGUF entry still wins over its parent, and a speculative-decoding drafter still does not inherit its target.
  • MCP handshake accepted by every schema-validated server (abstractcore/mcp/client.py). initialize now declares capabilities: {} as the specification and the reference client do; the previous envelope sent five capabilities set to null, which strict servers such as Context7 refused ("Invalid input: expected record, received null"), so their tools never reached the model. A 404 to a request carrying MCP-Session-Id now starts a new session with a fresh initialize and replays the request once, as the Streamable HTTP transport requires after a server restart. McpHttpError carries status_code.
  • An unreachable endpoint is reported as such, never as a spent timeout (abstractcore/providers/base.py, abstractcore/core/retry.py, abstractcore/exceptions). When no TCP connection to the provider's endpoint can be made (machine off or asleep, connection refused, DNS failure), providers raise the new EndpointUnreachableError with base_url, the transport exception class (cause), errno, the measured elapsed_s and retryable (False when the connect attempt itself timed out). Hosts can import it by name to park the step and probe the endpoint instead of failing the run. Such failures no longer count toward the circuit breaker, and a connect that timed out is not retried (a second attempt would block for the same OS budget). Timeout detection is type-first: the message is consulted only for exceptions that carry no type information, so an OSError whose text says "Operation timed out" no longer prints "timed out after 7200.0s (configured timeout)". Every normalisation logs the original exception class, and the "Generation failed" line reports the elapsed time from the first attempt (it used to print ~0 ms for every failure).
  • A stored speculation default never fails a call (abstractcore/providers/speculation.py). When require_acceleration=True comes from the provider-lifetime default (constructor speculation=, a stored profile or host setting) and the provider has no native MTP adapter, the call runs without speculation with one warning, and metadata["speculation"] carries applied: false and degraded_from_default: true. An explicit per-call require_acceleration=True still raises SpeculationUnavailableError.
  • Residency snapshot during an embeddings import (abstractcore/providers/process_residency.py). The in-process residency view treated abstractcore.embeddings.manager as loaded as soon as it appeared in sys.modules, which is true while another thread is still importing it, and failed with "partially initialized module has no attribute". The backend counts as loaded only once its functions exist.
  • Tool parameters carry their meaning (abstractcore/tools/core.py, abstractcore/tools/parser.py). The tool schema built from a decorated function now takes each parameter's description from the docstring's Args: section (Google style, or :param name: lines); it used to emit the type and default only, so native tool payloads and prompted tool lists showed the model bare parameter names. Native payloads carry the full text as JSON Schema description; the prompted tool list shows each parameter's first sentence. An explicit description set on the schema afterwards still wins. Every built-in tool parameter is now described, and a test keeps it that way.

[2.34.0] - 2026-11-03

Added

  • A model no call has used for 60 minutes is unloaded; a kept-loaded model never is (providers/process_residency.py, core ADR 0012, root backlog 1115).
  • Scope: HuggingFace (transformers and GGUF), MLX and in-process embedding models are unloaded by the process-wide eject (every holder, gc, the allocator cache) after the idle-unload time. The default is 60 minutes (DEFAULT_IDLE_UNLOAD_S = 3600).
  • Setting: set_idle_unload(seconds) sets the time for the process (0 or None: off); get_idle_unload() reads it.
  • What keeps a model: never a locked model (Keep loaded), never one a call runs on, never one a claimant is still building.
  • Never cancels: new calls to the model wait during the unload, the model is checked again with them held, and a call that started in between keeps it. A waiting call then reloads the model on demand. No check runs while a model loads.
  • Log and timer: each unload logs unloaded <model> after <N> min idle; freed <X.Y GB> (seconds under two minutes). The timer starts with the first load in the process; one reaper thread runs per process.
  • Rows: resident_model_states() covers MLX and embeddings too (also for the ADR 0010 fit failsafe), with last_used_at, in_use, locked_by and idle_unload_at.

Changed

  • Docs and the agent skill describe 2.34.0 (skills/abstractcore/, llms.txt, docs/native-mlx-runtime.md). The skill (package-version 2.34.0) teaches the idle unload and the one-provider rule for a caller's key on the discovery routes; docs/native-mlx-runtime.md no longer calls the shipped AbstractRuntime integration unreleased.

Fixed

  • The release-PR changelog check refuses an empty release section, and sees every fragment (scripts/changelog.py). A release PR whose ## [X.Y.Z] - <date> section had no entries passed when its fragments were deleted without being assembled; only the tag-time validation would have caught it. It now fails, naming the version. fragment_files reads changelog.d/**/*.md in any case (README excluded), so a fragment left in a subfolder or named fix.MD is listed by check and written by assemble, no longer invisible. On an ordinary PR, only such a .md file counts as the fragment a source change needs: a notes.txt under changelog.d/ used to satisfy the check, and assemble would never have read it. Entries are - bullets.
  • The web console's theme copy is re-synced to ui-kit 0.9.14 and a stale copy fails CI everywhere (console/theme_sync.py, console/themes.py, core backlog 0869).
  • themes.py records the ui-kit version it was generated from (KIT_SOURCE_PROVENANCE["kit_version"]), and a test compares it with theme_sync.KIT_THEME_FLOOR (0.9.14) without the abstractuic checkout. Before, the only check was the byte-for-byte drift test, which skips when the kit source is absent (as in CI).
  • The responsive token layer copies only bare :root (or :root[attr]) rules. A component rule written under :root (:root .af-session-card.af-automation-card, new in ui-kit 0.9.14) is no longer taken for a token.
  • Every call counts as in use and stamps the model's last use (providers/generation_cancel.py).
  • Before, a call without a cancel event was not registered and did not stamp last_used_at, so it could look idle while it ran.
  • MLX now gives every call a private cancel event, as HuggingFace does.
  • Embedding managers stamp their last encode.
  • The MLX ttl_s / keep_alive warning names the process-wide idle unload.

Security

  • A caller's provider key on a discovery route reaches only the provider the request names (server/app.py, root backlog 0955).
  • Before, X-AbstractCore-Provider-API-Key on /v1/capabilities and the capability and music discovery routes was handed to every key slot the capability has (OpenAI and the OpenAI-compatible server for voice, AceMusic and ElevenLabs for music, all of them on /v1/capabilities), so a key meant for one vendor could reach another.
  • Now the key goes to one provider: the one named with ?provider=<id> (voice: openai or an OpenAI-compatible server; music: a backend such as acemusic, and the request's registry uses only that backend), else the configured music backend, or the single vision endpoint.
  • A request that sends the key without naming one provider (GET /v1/capabilities, GET /v1/capabilities/voice/providers, an unknown music provider) is refused with 400 and the key reaches nobody. Authenticate to the server and leave the key out to list every provider.
  • Keys the server holds follow their own rule, unchanged: a request without its own key spends them only when it is server-authenticated (otherwise 401 while the server holds a key the route could spend).

[2.33.0] - 2026-11-03

GGUF prompt-cache snapshots without their unused scores copy and under a byte budget, a typed ModelNotDownloadedError, an OpenAI-compatible key check that refuses a wrong key where the model list is public, hosted decision models listed and routed as decision models (and a decision model that answers its own decisions), and a config that keeps a provider profile it cannot read instead of resetting itself.

Added

  • A model that is not downloaded raises ModelNotDownloadedError, which names it (abstractcore.exceptions). A subclass of ModelNotFoundError with model (the id to download) and provider (the provider that serves it) as attributes, so a host says "download X" without parsing the message (the gateway recovered the embedding model's id from the message text). The messages keep their wording. Raised where a local-only load finds nothing on this computer: embeddings (EmbeddingManager), transformers (not cached, or a download that did not finish), GGUF, MLX, and an MLX drafter. Existing except ModelNotFoundError handlers still catch it.

Changed

  • AbstractVoice floor 0.20.0 (pyproject.toml: the base install, [apple] and [gpu]; ABSTRACTVOICE_ENGINE_RUNTIME_FLOOR).
  • The changelog check recognises a release pull request (scripts/changelog.py check). A PR that bumps abstractcore/utils/version.py to X.Y.Z, adds CHANGELOG.md's dated ## [X.Y.Z] - YYYY-MM-DD section and leaves no fragment in changelog.d/ passes. Before, every release PR was red, because it edits CHANGELOG.md and source without adding a fragment. A release that leaves a fragment behind fails and names it. Any other PR that touches abstractcore/ still needs a fragment.
  • A GGUF model that is not downloaded now reaches the caller as ModelNotDownloadedError, not as a RuntimeError("Failed to load GGUF model ...") wrapping it; the message is the same "not found in local caches" text without that prefix. An MLX model that is not downloaded keeps its own message (the caches searched and the download tip) instead of the generic "Model not found for MLX provider" list.
  • The test suite never fails on a slow machine (tests/timing.py, ABSTRACTCORE_TIMING_STRICT). Every elapsed-time assertion in tests/ was audited. A "did not block" check became an event or state check:
  • the slot pool's dropped holder: the blocked work is still running when gc.collect() returns;
  • the cancelled slot request: at most one token after the cancel;
  • execute_command's drains: below the child's own sleep 30/40, the wait the code must not do;
  • the retry that fails fast: below the 30 s backoff.

Latency budgets (cancel promptness, ReDoS guards, streaming overheads, live-provider response times) go through timing_budget: one [timing] line on stderr by default, asserted only with ABSTRACTCORE_TIMING_STRICT=1, mirroring the gateway's tests/timing.py. The session's terminal summary lists every measure ("timing budgets", over-budget first), so the numbers are in every CI log. A blowup guard also passes ceiling=: a generous bound asserted always (a ReDoS regression is never a slow green). Test-only.

Fixed

  • A key check on an OpenAI-compatible endpoint with a public model list checks the KEY (openai_compatible_provider.py). OVH AI Endpoints answers GET /v1/models with 200 for no key and for a wrong one (measured 2026-10-29), so the gateway's Connect said "Connected · N models" to a wrong key. With raise_on_error=True (a key check) and a key set, when /models also answers WITHOUT the key, the listing now asks POST /chat/completions for a model that does not exist (abstractcore-key-check, nothing is generated): 401/403 raises AuthenticationError with the service's reason (OVH: 403 "authentication failed"); any other answer (404 "model not found") keeps the key. An endpoint whose /models needs the key (Mistral, Groq, …) is not probed; plain listing is unchanged; OpenRouter keeps its GET /key check (PUBLIC_MODELS_KEY_PROBE = False). Tests: tests/providers/test_compatible_key_probe_unit.py.
  • Hosted decision models are listed as decision models, and only there (providers/typesafe_provider.py, server/app.py). GET /v1/models showed typesafe/jev-latest (and any systemone model) as a text model (capabilities.output: ["text"], no decision block), and listed it under every capability filter, so text, image and embedding model pickers offered it and a chat on it then failed with decision_model. The typesafe and systemone providers now list their models only for a filter a decision model satisfies (input.text, output.decision), and /v1/models gives their entries capabilities: {input: [text], output: [decision]} and decision: {endpoint: /v1/decisions, kind: systemone, ...}, like the local Kev, Lev and Laya models.
  • An output.decision default on the hosted Jev runs the hosted Jev (providers/base.py, decision/pool.py). With the default set to provider typesafe and model jev-latest, a decision from a workflow (or any generate(..., output="decision") on a text provider) read jev-latest as the alias of the most recently used local decision model: it ran that local model instead, or failed with "names no resident decision model yet" when none was loaded. kev-latest / jev-latest are aliases only on a local route; on typesafe and systemone they are the hosted model's own name.
  • A decision model answers its own decisions; the output.decision default is for models that cannot decide (providers/base.py _decisions_stay_on_this_model). Before, with a default of typesafe + jev-latest, a local Kev instance (create_llm("mlx", model="…kev…").generate(doc, output="decision", questions=…), no route) sent the document to the hosted Jev because of a global setting. Now an instance whose own model is a decision model (a local Kev / Lev / Laya checkpoint on mlx or huggingface, or a typesafe / systemone instance) answers itself when the request names no decision provider or model. A route the request names still wins, and a text model still uses the default. Review of #41, Q1.
  • A GGUF prompt-cache eviction no longer clears a cache that a prefill is reading (huggingface_provider.py). prompt_cache_fork / prompt_cache_set store a cache from the caller's thread. The store's after-set hook enforces the snapshot byte budget, and evicting a key clears that key's cache_state. Neither took the GGUF prompt-cache lock, so a prefill holding the lock on another thread could fail with "OrderedDict mutated during iteration" or miss its restore. The count-based LRU eviction had the same gap. Both store hooks now take _gguf_prompt_cache_lock, now a reentrant lock (the save site holds it while the eviction it triggers runs the hooks). Review of #37, M1.
  • A GGUF prompt-cache snapshot no longer carries half a gigabyte it never uses, and the snapshots stay under a byte budget (8080 pass four, 2026-10-29: the model host child grew 1.65 GB per basic-agent run, 4.60 to 9.57 GB in three runs). Llama.save_state copies a scores array of n_batch x n_vocab float32 into every snapshot, 508 MB for a Qwen3.5 vocabulary. With logits_all=False llama.cpp never writes or reads that array, and nothing counted it, so the stats showed 0.42 GB of caches per run while 1.5 GB more stayed resident. A stored snapshot now keeps one zero row, which load_state broadcasts; with logits_all=True the array is kept whole. Per-key bytes and cache_state_total_bytes count the arrays too. The snapshots of every key together are held to gguf_prompt_cache_max_gb in the AbstractCore config (GiB; the environment variable ABSTRACTCORE_GGUF_PROMPT_CACHE_MAX_GB overrides it; default min(8 GiB, a quarter of physical RAM), the MLX prefix cache's rule; documented in docs/centralized-config.md, Model Memory). The least recently used keys are evicted on every insert path through a new PromptCacheStore on_set hook and evict(), and get_prompt_cache_stats()["gguf"] reports prompt_cache_budget_bytes and prompt_cache_total_bytes. Measured on a Mac with unsloth/Qwen3.5-4B-GGUF through a real gateway (--model-host process), ten basic-agent runs:
  • before: child RSS 14.77 to 29.95 GB, +1.69 GB a run;
  • after: 13.28 to 15.69 GB, +0.27 GB a run while keys accumulate;
  • with a 1.5 GiB budget: the caches hold at 1.61 GB from run 5 to run 15, and RSS stays within 11.2 to 13.5 GB.

A restore from a compacted snapshot answers token for token like a cold prefill (tests/providers/test_gguf_snapshot_restore_real.py, opt-in ABSTRACTCORE_RUN_GGUF_TESTS=1): the provider never samples from restored logits, because a restore covering the whole prompt is rolled back one token and that token is decoded (the zero-feed guard in _gguf_prefill_prompt_cache, pinned by a unit test). - A provider profile whose family this AbstractCore does not know no longer makes the whole config read as corrupt (config/provider_profiles.py, config/manager.py). 2026-11-03: the abstractcore 2.31 installs in the gateway and assistant environments (whose family list predates typesafe/systemone, added in 2.32.0) read a config holding a TypeSafe connection. The row's "Unsupported provider family 'typesafe'" error quarantined the file (a .corrupt-<stamp>.bak copy on every import) and ran the session on DEFAULTS, without any of the other profiles or settings. Such a row is now skipped with one WARNING naming it ("provider profile 'typesafe-key' is not loaded by this AbstractCore (...); it stays in the config file unchanged"). The rest of the config loads, nothing is written, and a later save keeps the row exactly as stored (the same carry that keeps a newer Core's route keys and columns). The same applies to any profile row that does not validate. typesafe and systemone are profile families since 2.32.0, derived from the provider registry. - The MLX owner-retirement tests prove "the GC callback did not block" with events, not a stopwatch (tests/providers/test_mlx_native_owner_retirement_unit.py). Three tests asserted that a whole gc.collect() took under 0.5 s. In the Local-model CI job, a full collection alone takes about 0.55 s (torch and transformers loaded, thousands of tests' objects alive), so main went red at 9d46642 and de1f9c85 with no MLX change. The tests now check that the blocked CPU backend, or the blocked close hook, has not returned when gc.collect() returns: a callback that waited for it could only return after it. There is no wall-clock bound, and the intent is unchanged. A mutant whose GC callback joins the worker turns all three red. Test-only.

[2.32.0] - 2026-11-02

Decision models (text in, calibrated typed decisions out: output="decision", POST /v1/decisions), one llama.cpp weights instance per GGUF with a per-model slot pool for concurrent requests, a reserved context computed from free memory and settable per model, shared embedding models, and a catalogue that lists every installed or cached asset by its exact identity.

Added

  • Every quant of a model, on demand (backlog 0865). catalog(hub=True, extended=True) and ?extended=true list, per row, every quant its own GGUF repos ship (UD-IQ1_S to Q8_0, BF16), each with its exact size and its fit, marked extended: true and never pre-selected. Labels the download pattern cannot fetch exactly are left out. gguf_quant_labels(facts) is the enumeration.
  • Model residency failsafe (ADR 0010): a load never fills the card. Before llama.cpp allocates (one full-offload CUDA card), the GGUF load checks weights + KV at its smallest context + the reserve against the free device memory; when it does not fit, resident models that are neither locked (a "Keep loaded" pin) nor in use are evicted, least recently used first, one at a time (process_residency.make_room); if it still does not fit, the load fails before allocating with ModelDoesNotFitError (needed_bytes, free_bytes, kept, evicted, suggestions: smaller artifacts of the same model from the catalog) and a sentence ("X needs 13.7 GB but only 9.2 GB is free on the GPU (kept: Y (locked by the runtime of account default/admin)). Choose a smaller model, for example ..."). The CPU fallback is checked against available RAM the same way. InflightGenerations.last_used_at and _residency_registered_at give the order.
  • Every cached asset appears in the catalogue (backlog 0875; catalog(), /acore/models/catalog). A local repository or engine model that matches no curated row is listed as a discovered row (source: "installed", id installed:<provider>:<reference>), with its exact reference, size, kind, tasks and their source, so local files stay manageable from one list. Each row carries asset_kind (model, adapter, component, unknown) and each artifact an inventory object (present, complete, kind, tasks, files, incomplete_files, missing_shards, bytes).   • A skipped eject names its holders in words (owner_label of the claim, "the runtime of account default/bob"), never "runtime client 70a5b844f350" (ADR 0043).

  • A prompt longer than the loaded GGUF context fails clearly, before any eval (ContextWindowExceededError, a subclass of InvalidRequestError): it used to fill the KV cache ("decode: failed to find a memory slot for batch of size 512"), retry cold, rebuild the engine and answer "Error: failed to prefill GGUF prompt cache ..." as text; llama-cpp-python's own "exceed context window" refusal is raised the same way. Decoding that reaches the end of the context stops with finish_reason="length" instead of appending "Error: llama_decode returned 1".

  • /v1/chat/completions (and /v1/responses) reuse a model already resident in the process instead of loading another copy per request (backlog 0859). With no model loaded in the server's own registry, the chat route called create_llm for every request; a host that keeps the model in another holder (AbstractGateway's runtime pool, which serves /v1 through this app) got a second full llama.cpp instance per request. Found on a fresh Linux install: a 2.5 GB GGUF on a 16 GB GPU answered 500 "Failed to create llama_context"; reproduced on Metal: holders 1 -> 2 -> 3 -> 4 and the process 11.2 -> 43.4 GB over three calls. Not with unload_after (it would unload the holder's model) nor with request-specific provider settings (an explicit provider key, a base_url); an instance the server built for one request is never lent; MLX instances already share weights and are not lent. A lent instance keeps its own tracing (no X-AbstractCore-Trace-Id for that request) and ignores the request's timeout_s.

  • Every operation on a HuggingFace provider instance's model runs on one worker thread of that instance, one at a time (HuggingFaceProvider._generation_worker): generations, the prompt-cache prefills, set/clear/save/load, the bloc planner's tokenization, load_model and the free step of unload_model. Before, only the GGUF prompt-cache prefill took an instance lock, so a pool serving two runs (or a run and a lent /v1 request) could run two operations on one llama.cpp context at once. A stream is produced on the worker into a queue, so it never waits for its consumer (no deadlock with a call waiting for the instance, or two streams advanced by one thread); a consumer that stops early stops the producer at its next chunk; a stream counts as in flight from the call (an unload cancels and waits for it); the reload of an ejected model is decided on the worker; the caller's contextvars travel with the call; Ctrl-C while waiting cancels the generation.
  • A lent instance answers /v1 off the event loop, with a client disconnect cancelling its generation (it queues behind the holder's runs; the server's own in-process instances still answer on the loop as before). It keeps its holder's construction defaults (seed, default max output tokens, context size) for settings the request omits, shares the holder's prompt-cache store (by default 32 entries, least recently used), and, when the holder has tracing on, its trace buffer.
