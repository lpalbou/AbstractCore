Decision Models

Decision models answer typed questions about a document with calibrated probabilities instead of generating text. AbstractCore surfaces them as the decision output modality — text in, decisions out — behind one abstraction that does not depend on any single model or vendor:

Table of Contents

What a decision model returns Quick start Over HTTP: POST /v1/decisions Providers, models and formats Measured quality and speed Limits Related
  • Hosted: TypeSafe's Jev (typesafe provider) and any System One-compatible endpoint, that is any server speaking the public System One decision API (systemone provider: a self-hosted Kev or Lev process, another AbstractCore server, or another host). Nothing but httpx; the light install is enough.
  • Local: the Kev family (pointer head on Qwen3.5), Lev (label logits on Qwen3.5-4B) and Laya (ModernBERT encoder with a marker scorer), all Apache-2.0, on the mlx provider (Apple silicon) and the huggingface provider (transformers, or a GGUF through llama.cpp). OpenJev-style checkpoints run through the same label-logit engine (their weights are CC-BY-NC-4.0).

The request, the answers and the HTTP surface (POST /v1/decisions) are the same for every one of them, so you switch models and providers without changing your code. Use a decision model when you classify, route, triage, score, or check documents and need probabilities you can threshold — send the uncertain cases to a human, automate the rest. Kev-4B answers several questions about a support ticket in about 100 ms on Apple silicon; Laya in about 50 ms on a laptop CPU/GPU; no prompt engineering and no output parsing.

What a decision model returns

One request carries one state (the document: a string, or a JSON object/array rendered as labelled text) and any number of named questions. Each question has one of three types:

Type You supply You get
choice 1–255 named options, each with an optional description the most likely option (choice), probabilities per option, confidence
noul a statement in instructions (optional criteria describing true / false) noul: the probability that the statement is true
score 1–255 ordered levels, lowest first score: the expected level index, probabilities per level, legend, confidence

Questions never influence one another: every question is scored against the state alone. The model only ever scores the options you give it; it never writes an option of its own. Confidence is derived from the distribution (0 at uniform, 1 at certainty) and follows the System One reference conventions, so answers are comparable across hosted and local decision models.

Quick start

Download the model once (no silent downloads: AbstractCore loads only what is on disk):

# Apple silicon (MLX) or transformers: the adapter + its base model
abstractcore models download mlx jaredpalmer/kev-4b
abstractcore models download mlx Qwen/Qwen3.5-4B-Base
# or the self-contained GGUF (llama.cpp), 3 GB
abstractcore models download huggingface "ggml-org/Kev-4B-GGUF:Q4_K_M"

Then ask:

from abstractcore import create_llm

llm = create_llm("mlx", model="jaredpalmer/kev-4b")   # or ("huggingface", model="ggml-org/Kev-4B-GGUF:Q4_K_M")

ticket = "Shoes arrived two weeks late and in the wrong size. Also I see two charges on my card."
result = llm.generate(ticket, output="decision", questions={
    "department": {"type": "choice", "instructions": "Which team should handle this?",
                   "criteria": {"returns": "Exchanges, refunds, wrong or damaged items",
                                "shipping": "Delivery status, delays, lost packages",
                                "billing": "Charges, invoices, payment problems"}},
    "escalate":   {"type": "noul", "instructions": "Does this need urgent human attention?"},
    "frustration": {"type": "score", "instructions": "How frustrated is the customer?",
                    "criteria": ["Calm", "Frustrated", "Very angry"]},
})

result.decisions["department"].choice          # "returns"
result.decisions["department"].probabilities   # {"returns": 0.51, "shipping": 0.36, "billing": 0.13}
result.decisions["escalate"].noul              # 0.72
result.decisions["frustration"].score          # 1.30  (between "Frustrated" and "Very angry")
result.decision.to_systemone()                 # the System One response body

The document is read once per request and reused for every question in it, and the last four documents stay cached, so consecutive requests about the same document only pay for their questions (Kev-4B 8-bit on an M5 Max: a 6,300-token contract costs 1.4 s the first time and 0.1 s again; a 100-token ticket 95 ms then 45 ms). create_llm(..., decision_prefix_cache_size=0) disables the cache, a larger value keeps more documents; every decision_<option>= kwarg reaches the decision loader.

generate(..., output="decision") returns a MultimodalGenerateResponse whose decision is a DecisionResponse (answers, usage, latency_ms) and whose decisions property is the answers keyed by question name. result.content is the answers as JSON, so sessions and logs that read text still see something meaningful. The state is the prompt; pass state= (any JSON) to render an object instead.

Python shorthand is accepted for questions: a string is a noul statement, a list of names is a choice with no descriptions, {"instructions": ..., "levels": [...]} is a score:

llm.generate(ticket, output="decision", questions={
    "team": ["returns", "shipping", "billing"],
    "urgent": "Does this need urgent human attention?",
    "mood": {"instructions": "How frustrated is the customer?", "levels": ["Calm", "Frustrated", "Very angry"]},
})

A decision model has no text lane: generate("hello") on it raises with a pointer to output="decision". Text generation on other models is unchanged.

From any provider, through the default route

Set the output.decision capability default once and every provider instance that cannot decide itself (a text model) can answer output="decision", the way output="voice" runs the configured voice engine. An instance whose own model is a decision model (a local Kev, or a typesafe / systemone instance) always answers itself unless the request names a route, so a hosted default never receives a document a local decision model was asked about:

abstractcore config set-default output.decision --provider mlx --model jaredpalmer/kev-4b

llm = create_llm("ollama", model="qwen3.5:9b")           # a text model
result = llm.generate(ticket, output="decision", questions={...})   # answered by the configured Kev

The route resolver puts the configured provider and model on the output spec; the decision lane runs them through the process-wide pool (abstractcore.decision.pool): at most two decision models stay loaded, the least recently used is unloaded, and the server's /v1/decisions shares the same pool, and a model a request is using is never unloaded under it. An explicit route on the spec wins over the default: output={"modality": "decision", "provider": "mlx", "model": "jaredpalmer/kev-0.8b"}, or a provider/model handle in model ("huggingface/ggml-org/Kev-4B-GGUF:Q4_K_M"), while a bare model picks the local engine (a GGUF on huggingface, else mlx when mlx-lm is installed) and kev-latest reuses the most recently used resident model. decision_* route options (decision_prefix_cache_size, decision_n_ctx, ...) reach the loader. With no route and no default, a provider that is not itself a decision model raises an error that names the set-default command. The answers' model is always provider/model.

Without a provider object

from abstractcore.decision import load_decision_model

model = load_decision_model("mlx", "jaredpalmer/kev-4b")
response = model.decide(ticket, {"urgent": "Does this need urgent human attention?"})
response["urgent"].noul

load_decision_model(provider, model) is cache-only; pass allow_download=True to fetch the snapshot (and the base model of an adapter) first.

Over HTTP: POST /v1/decisions

The AbstractCore server answers decisions at POST /v1/decisions with the System One request and answer shape (the format every decision-model host shares; /{provider}/v1/decisions takes an unprefixed model). The Python shorthand works on this route too (a string question is a noul, a list of option names a choice); hosted System One servers take only the typed form:

curl -s http://localhost:8000/v1/decisions -H 'content-type: application/json' -d '{
  "model": "mlx/jaredpalmer/kev-4b",
  "state": "Shoes arrived two weeks late and in the wrong size. Also I see two charges on my card.",
  "questions": {
    "department": {"type": "choice", "instructions": "Which team should handle this?",
                   "criteria": {"returns": "Exchanges, refunds, wrong or damaged items",
                                "shipping": "Delivery status, delays, lost packages",
                                "billing": "Charges, invoices, payment problems"}},
    "escalate":   {"type": "noul", "instructions": "Does this need urgent human attention?"},
    "frustration": {"type": "score", "instructions": "How frustrated is the customer?",
                    "criteria": ["Calm", "Frustrated", "Very angry"]}
  }}'

{"model": "mlx/jaredpalmer/kev-4b",
 "answers": {
   "department": {"type": "choice", "choice": "returns", "confidence": 0.2681,
                  "probabilities": {"returns": 0.5121, "shipping": 0.3554, "billing": 0.1326}},

GET /v1/models?output_type=decision lists the decision models the server can reach; each entry carries capabilities (input / output) and a decision object naming this endpoint. A chat completion against a decision model is refused with a 400 that points here: OpenAI has no shape for calibrated typed decisions, and the System One format is the one every decision-model host shares.

model takes provider/model (mlx/jaredpalmer/kev-4b, huggingface/ggml-org/Kev-4B-GGUF:Q4_K_M, huggingface/jaredpalmer/kev-4b). A bare handle picks the local engine (mlx on Apple silicon when mlx-lm is installed, otherwise huggingface); kev-latest and jev-latest reuse the decision model this server loaded most recently, else the configured output.decision default. The first request loads the model, later ones reuse it, and the server keeps the two most recently used decision models resident (the same pool generate(output="decision") uses in that process). The pool is part of the model residency API: POST /acore/models/load with {"task": "decision", "model": "mlx/jaredpalmer/kev-4b"} loads a decision model ahead of the first request, GET /acore/models/loaded?task=decision lists the resident ones (process:decision:<provider>:<model> rows), and POST /acore/models/unload releases one. Errors: 400 for an invalid request, 404 when the model is not downloaded, 422 when the state is over the context limit.

Decision kinds

A kind is a readout mechanism; every checkpoint of a kind shares its prompt layout and how the probabilities are read, and differs only in weights and calibration:

  • kev — five delimiter tokens pack the state and each question; a pointer head scores every option's end token against the question's decide token. The state is computed once and cached; each question only pays for its own tokens.
  • lev — a chat prompt lists the options under letters; the answer is read from the next-token logits of the label tokens. A choice is read in two option orders and averaged; a yes/no is a 0–8 rating. The adapter runs at a quarter of its trained strength, as released. The tokens every prompt of a request shares (system text and state) run once and are reused for every question and option order, on transformers, mlx-lm and llama.cpp alike.
  • openjev — the same mechanism with one letter per option (up to 52 options) and fixed temperatures.
  • laya — one bidirectional ModernBERT pass per question ([CLS] question [SEP] [MASK] option … [SEP] state [SEP], 512 tokens), a two-layer head and a scorer at each [MASK]. A state longer than the room the questions leave is scanned in overlapping windows (half-window stride) and the windows are combined as Laya's own runtime does: a yes/no is the maximum P(true) over windows, a choice or score is the most confident window's distribution (long_state="truncate" reads the start only). The number read is the deciding window's, not a calibration over the whole document.
  • systemone — a remote endpoint; the host decides.

Artifact layouts

  • Adapter (jaredpalmer/kev-4b, interfaze-ai/lev): the published LoRA; needs its base model on disk (download both). AbstractCore folds the adapter into the base at load (about a minute for a 4B model).
  • Merged (an AbstractCore conversion, or a complete checkpoint such as convaiinnovations/laya): loads directly, in transformers or mlx-lm layout, bf16 or quantized.
  • GGUF (ggml-org/Kev-4B-GGUF, ggml-org/lev-GGUF, ggml-org/OpenJev-GGUF): llama.cpp's conversions. Lev and OpenJev read ordinary logits and run on every released llama-cpp-python. Kev's GGUF carries its pointer head inside the file. On a llama-cpp-python that bundles llama.cpp from 2026-10-02 or later (ggml-org/llama.cpp#29818) it loads as is; on every current release AbstractCore derives once, next to its model cache, a backbone copy of the file without the head (every other tensor copied byte for byte) and applies the head itself, with the same numbers. Nothing to install beyond abstractcore[apple] / [gpu]; the first load of a file takes a few seconds longer. (This bridge goes away with abetlen/llama-cpp-python#2398.) Laya's GGUF needs llama.cpp's decision graph and is not run by AbstractCore yet; use the transformers checkpoint.

The AbstractFramework conversions on the Hub (collection Decision models) are these recipes applied to Kev-4B and Kev-0.8B: kev-4b-mlx-8bit (4.2 GB), kev-4b-mlx-4bit (3.0 GB), kev-0.8b-mlx-8bit (0.8 GB), kev-0.8b-mlx-4bit. Convert a Kev adapter yourself with:

python -m abstractcore.decision.convert jaredpalmer/kev-4b --runtime mlx --bits 8 --out ./kev-4b-mlx-8bit
python -m abstractcore.decision.convert jaredpalmer/kev-4b --runtime mlx --bits 4 --group-size 32 \
    --upgrade '{"linear_attn.in_proj_qkv": 8, "linear_attn.in_proj_z": 8, "linear_attn.in_proj_a": 8, "linear_attn.in_proj_b": 8, "linear_attn.out_proj": 8}' \
    --out ./kev-4b-mlx-4bit
python -m abstractcore.decision.convert jaredpalmer/kev-4b --runtime transformers --out ./kev-4b
# Kev-0.8B is more sensitive: keep the MLP gate/up projections at 8-bit as well
python -m abstractcore.decision.convert jaredpalmer/kev-0.8b --runtime mlx --bits 4 --group-size 32 \
    --upgrade '{"linear_attn.in_proj_qkv": 8, "linear_attn.in_proj_z": 8, "linear_attn.in_proj_a": 8, "linear_attn.in_proj_b": 8, "linear_attn.out_proj": 8, "mlp.gate_proj": 8, "mlp.up_proj": 8}' \
    --out ./kev-0.8b-mlx-4bit

The second command is the measured 4-bit recipe (group size 32, the Gated DeltaNet projections at 8 bits): a plain 4-bit conversion of a decision model loses accuracy and shifts probabilities; this one keeps the accuracy and most of the calibration (table below). When calibration matters more than size, use 8-bit: it is indistinguishable from bf16. A converted folder is a plain model handle: create_llm("mlx", model="./kev-4b-mlx-4bit").

What the ladder says: the hosted model holds its accuracy across the whole range and stays flat in latency; the 4B local models match it on clause presence up to 16k tokens (within the noise of a few dozen questions) but lose reading comprehension beyond 4k, where their authors' training states stopped. Kev-0.8B is four times faster than Kev-4B at every length (1.3 s for a 16k-token contract) and keeps most of the clause-presence accuracy, but not reading comprehension past 2k. On every local engine the state is read once per request and reused for all its questions and option orders (the pointer-head cache for Kev, the shared prompt prefix for Lev), so a second request about the same document only pays for its questions; Kev-4B's 4-bit checkpoint keeps the bf16 accuracy at a somewhat higher prefill cost on MLX. Local latency grows linearly with the document: a 16k-token contract costs about five seconds on an M5 Max, once per document, after which more questions about it cost tens of milliseconds.

How to read the numbers

  • Argmax agreement with the bf16 run is what a classifier or router sees; |Δp| is what a threshold sees. 8-bit (MLX or Q8_0) is indistinguishable from bf16. The official Q4_K_M GGUF and the mixed MLX 4-bit recipe keep the accuracy; a few percent of their answers move by more than 0.10 against bf16, so prefer 8-bit when you threshold probabilities. The plain 4-bit recipe (every linear at 4 bits, group 64) loses a point of accuracy and moves a tenth of the answers by more than 0.10; it is not offered.
  • The Kev model card reports its own figures for Kev-4B (new-source accuracy 0.82–0.84, trained-source 0.87) on the author's evaluation suites; they are not reproduced here. The tables above are measured on the public pool, which mixes trained and new sources.

Limits

  • Kev and Lev are English only (Laya ships a multilingual checkpoint); knowledge questions are bounded by the 4B base (the author reports MMLU-Pro 0.59 for Kev-9B against 0.84 for Jev).
  • A state may hold up to 65,536 tokens and each question row 8,192 tokens more; an over-long state is refused (ContextOverflow, HTTP 422) unless you ask to truncate. The author trained on states up to 7,552 tokens, so accuracy on much longer documents is not characterised.
  • Changing the order of a question's options can change its answer; keep option order stable when you compare runs.
  • Calibration is the author's: one temperature per checkpoint for Kev (2.41 for Kev-4B), per question type and option count for Lev and Laya; a temperature never changes which option ranks first. A hosted model's calibration is the host's.
  • Decision models never generate text: response_model=, tools, streaming and media inputs do not apply to output="decision".
